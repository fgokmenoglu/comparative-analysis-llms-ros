ROS 2 Autonomous Mobile Robot Architecture
Executive Summary
This architecture implements a complete navigation stack for a differential drive robot with 2D LiDAR, utilizing ROS 2's Nav2 framework for robust autonomous navigation in known environments with dynamic obstacle avoidance.
________________________________________
1. Node Architecture
Hardware Interface Layer
lidar_driver_node
•	Package: Sensor-specific (e.g., urg_node, sllidar_ros2)
•	Responsibility: Interfaces with 2D LiDAR hardware, publishes laser scan data
•	Frequency: 10-20 Hz typical
base_controller_node
•	Package: Hardware-specific or diff_drive_controller
•	Responsibility: Translates velocity commands to motor commands, publishes odometry from wheel encoders
•	Frequency: 50-100 Hz for odometry
________________________________________
Localization Layer
map_server
•	Package: nav2_map_server
•	Responsibility: Loads and serves the static occupancy grid map, provides map metadata
•	Lifecycle: Typically runs continuously once configured
amcl (Adaptive Monte Carlo Localization)
•	Package: nav2_amcl
•	Responsibility: Estimates robot pose on the map using particle filter with laser scans and odometry
•	Output: Publishes transform from map → odom frame
________________________________________
Navigation Layer
planner_server
•	Package: nav2_planner
•	Responsibility: Computes global path from current pose to goal using algorithms like NavFn, Smac Planner, or Theta*
•	Trigger: On-demand when new goal received or replanning needed
controller_server
•	Package: nav2_controller
•	Responsibility: Local trajectory generation and dynamic obstacle avoidance (DWB, TEB, RPP, MPPI controllers)
•	Frequency: 10-20 Hz for velocity command generation
bt_navigator
•	Package: nav2_bt_navigator
•	Responsibility: Orchestrates navigation behaviors using behavior trees (goal checking, recovery, replanning)
•	Role: High-level mission controller
behavior_server
•	Package: nav2_behaviors
•	Responsibility: Executes recovery behaviors (backup, spin, wait) when robot gets stuck
waypoint_follower
•	Package: nav2_waypoint_follower
•	Responsibility: Manages sequential navigation through multiple waypoints
•	Optional: Only needed for multi-goal missions
________________________________________
Perception Layer
costmap_2d (Global & Local)
•	Package: nav2_costmap_2d
•	Responsibility: 
o	Global Costmap: Static map-based costs for global planning
o	Local Costmap: Rolling window with real-time obstacle detection for local planning
•	Layers: Static layer, obstacle layer, inflation layer, (optional) voxel layer
________________________________________
Support Nodes
robot_state_publisher
•	Package: robot_state_publisher
•	Responsibility: Publishes robot URDF transforms (base_link → laser_frame, etc.)
lifecycle_manager
•	Package: nav2_lifecycle_manager
•	Responsibility: Manages lifecycle transitions (configure, activate, deactivate) for Nav2 nodes

3. Data Flow Explanation
Startup Sequence
1.	Static Transforms: robot_state_publisher broadcasts URDF-based transforms (base_link → laser_frame)
2.	Map Loading: map_server loads occupancy grid and publishes to /map
3.	Initialization: User provides initial pose via /initialpose for AMCL particle filter initialization
________________________________________
Continuous Localization Loop
LiDAR Hardware → /scan (LaserScan)
                    ↓
Wheel Encoders → /odom (Odometry)
                    ↓
              ┌─────▼────────┐
              │     AMCL     │ (Particle filter)
              └─────┬────────┘
                    ↓
            /tf (map→odom transform)
Flow: AMCL fuses wheel odometry (short-term accurate) with laser scans matched against the static map to estimate the map→odom transform, correcting odometry drift.
________________________________________
Navigation Execution Flow
Phase 1: Goal Reception & Global Planning
User/Mission → /goal_pose
                    ↓
              ┌─────▼────────┐
              │ BT Navigator │ (Behavior tree orchestration)
              └─────┬────────┘
                    ↓
         [Action] navigate_to_pose
                    ↓
           ┌────────▼──────────┐
           │  Planner Server   │
           │  + Global Costmap │
           └────────┬──────────┘
                    ↓
              /plan (Path)
Global Costmap Construction:
•	Static layer from /map
•	Inflation layer adds safety margins
•	Result: Cost grid for collision-free planning
________________________________________
Phase 2: Local Planning & Control Loop
/plan (Global path) ──┐
                      ↓
/scan (LaserScan) ──► ┌────────────────────┐
                      │ Controller Server  │
/odom (Odometry) ───► │ + Local Costmap    │
                      └──────────┬─────────┘
/tf (Localization) ──►           ↓
                           /cmd_vel (Twist)
                                  ↓
                      ┌───────────▼──────────┐
                      │ Base Controller Node │
                      └───────────┬──────────┘
                                  ↓
                          Motor Commands
Local Costmap Construction (rolling window around robot):
1.	Obstacle Layer: Raycasts /scan data to mark obstacles
2.	Inflation Layer: Adds graduated costs around obstacles
3.	Result: Real-time obstacle representation
Controller Operations:
1.	Receives global path from planner
2.	Samples velocity trajectories (linear + angular)
3.	Scores each trajectory against: 
o	Path alignment
o	Goal distance
o	Obstacle proximity (from local costmap)
4.	Selects optimal trajectory
5.	Publishes corresponding velocities to /cmd_vel at 10-20 Hz
________________________________________
Phase 3: Dynamic Obstacle Handling
/scan (new obstacle) → Local Costmap Update
                            ↓
                    Controller adjusts trajectory
                            ↓
                    If path blocked → Replan trigger
                            ↓
                    Planner Server computes new path
Real-time adaptation: Local costmap updates every cycle, allowing controller to reactively avoid dynamic obstacles without replanning (unless path fully blocked).
________________________________________
Transform Tree (TF)
map (world frame)
  └─ odom (drift-prone odometry frame) [published by AMCL]
      └─ base_footprint (robot ground projection)
          └─ base_link (robot center) [published by base_controller]
              ├─ laser_frame (LiDAR sensor) [static, from robot_state_publisher]
              └─ [other sensors/actuators]
Critical: All navigation nodes require valid map→base_link transform chain for coordinate conversions.
________________________________________
4. Architectural Patterns
Separation of Concerns
•	Localization: Where am I? (AMCL)
•	Planning: Where should I go? (Planner Server)
•	Control: How do I get there? (Controller Server)
•	Recovery: What if I'm stuck? (Behavior Server)
Layered Costmaps
•	Global: Strategic planning on static map
•	Local: Tactical obstacle avoidance with real-time sensor data
Action-Based Goals
•	Uses ROS 2 actions for cancellable, feedback-enabled navigation goals
•	Allows monitoring progress and preempting missions
________________________________________
5. Key Parameters to Tune
1.	AMCL: Particle count, motion/sensor noise models
2.	Global Planner: Algorithm choice (NavFn for speed, Smac for holonomic constraints)
3.	Local Controller: DWB parameters (velocity limits, trajectory sampling density, cost weights)
4.	Costmaps: Inflation radius, obstacle marking threshold, update frequency
5.	Behavior Trees: Recovery timeout thresholds, replanning triggers
________________________________________
This architecture provides a robust, modular foundation for autonomous navigation with clear separation between perception, localization, planning, and control—following ROS 2 and Nav2 best practices.
